## 四、本会话学到的新经验

### 子智能体审查流程的价值

- M2-1+M2-2 规格审查发现 FakeClient 与 execClient 错误返回语义不一致（FakeClient 返回 error，execClient 返回 nil）
- M2-1+M2-2 代码审查发现 args 切片别名问题和 parseVersion 应改用 strconv.Atoi
- M2-3 代码审查发现 UpdateRoot 空 revision bug
- M2-5 代码审查发现 Compute 丢弃 context.Context、Logger 未使用、DryRun 不设 StateAfter

**结论：** 两阶段审查（规格合规 + 代码质量）能持续发现实际问题，值得坚持。

### Compute 函数签名演进

- 初始实现 `Compute(opts Options) (*Result, error)` 内部硬编码 `context.Background()`
- 审查发现后改为 `Compute(ctx context.Context, opts Options) (*Result, error)`
- **教训：** 设计 API 时应从一开始就接受 context 参数，避免后续 breaking change

### buildState 的确定性

- `buildState` 遍历 map 产生非确定性顺序，但 `state.Save` 内部已排序
- 为 `Result.StateAfter.Paths` 的一致性，仍在 `buildState` 中排序
- **原则：** 即使下游会修正，生成数据时也应保证确定性
