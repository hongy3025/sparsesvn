## 四、已确认的设计决策（讨论过、不要再翻盘）

1. **包命名：** `internal/logx/`（不是 `log/`，避免与标准库冲突）
2. **path 去重区分大小写**：SVN 在多数文件系统区分大小写，配置 path 重复检测也区分大小写
3. **`C:\foo` 这类 Windows 绝对路径**：因含 `\` 被 validatePath 拒绝（正确，规格只允许正斜杠）
4. **`foo..bar` 这类含 `..` 但不是单独段**：允许（按 `/` 分段后再判断 `..`）
5. **YAML 显式 `path: ""` 或 `path:`**：都被 validatePath 拒绝
6. **yaml 解析策略：** 内部 `rawConfig` 中间层 + ParseDepth，**不**用 UnmarshalYAML 方法
7. **yaml strict/KnownFields 模式：** 未启用，未知字段静默忽略（如有需要后续任务再加）
8. **executor.Compute 是纯计算函数**，不依赖 Client，便于 plan/status 测试；只有 Apply 才需要 Client
9. **apply 子命令测试注入：** 通过 unexported `runApply(opts, client)` 接受 client 参数，FakeClient 注入

## 五、已建立的工作流惯例

### Commit message 风格

- Conventional Commits：`<type>(<scope>): <subject>`
- type：`feat` / `chore` / `refactor` / `docs` / `test` / `build` / `ci`
- scope：`config` / `state` / `plan` / `svn` / `cli` / `executor` / `logx`
- subject 全小写英文动词开头，无句号

### 错误信息风格（已统一）

- 英文小写动词开头：`fmt.Errorf("load config %s: %w", path, err)`
- 必含路径或上下文索引：`paths[%d] %q: %w`
- 用 `%w` 包装，**禁止**字符串匹配判错
- **不要**在内部函数错误信息加包名前缀（如 `"validate: ..."`），由外层统一加层级

### 测试风格

- 包名 `package config`（白盒，可访问内部 API）
- 临时目录用 `t.TempDir()`，文件用 `os.WriteFile`
- 错误断言用 `strings.Contains(err.Error(), "关键词")`，**禁止**完全字符串匹配
- table-driven 用 `t.Run(name, func(t *testing.T) { ... })` 让子用例独立报告
- YAML 字面量用反引号原始字符串（不要 `"\n"+"\n"` 拼接）
- 测试名前缀 `Test<Func>_<Scenario>`，如 `TestLoad_FileNotFound`

### Go 代码风格

- 函数 ≤ 50 行、嵌套 ≤ 3 层
- 导入分组：标准库 / 第三方 / 本项目（goimports 风格）
- 不引入计划外的导出 API
- defer Close 对只读文件可忽略错误
- IO 用流式（`io.Copy`），不要 `ReadAll` 整文件

## 六、已踩过的坑

1. **Makefile 缩进必须 tab**：用 `write` 工具写 Makefile 时，确认首个缩进字节是 `0x09`（tab），不是 `0x20`（space）
2. **Windows CRLF 警告**：所有 Git commit 都会出 `warning: LF will be replaced by CRLF`，可忽略（仓库内存储 LF）
3. **PowerShell 输出 UTF-8**：控制台默认 GBK 渲染会让中文显示为乱码，但**文件内容是真正的 UTF-8**，不要被误导。验证方式：`[System.Text.UTF8Encoding]::new($false, $true).GetString($bytes)` 不抛异常即合法
4. **`go.sum` h1 哈希自动补全**：测试编译时可能触发，会让 `go.sum` 出现未提交改动。直接 `git add go.sum && git commit -m "chore: complete go.sum h1 hashes"`
5. **`go.mod` indirect 标记**：第一次添加新依赖后跑 `go mod tidy` 会自动从 indirect 改为 direct，记得在每个新引依赖的任务最后跑 tidy
6. **race detector 在 Windows 需要 cgo+gcc**：本机环境无 gcc，无法跑 `-race`。新会话若仍是此环境，规格里说"运行 `go test -race`"应允许跳过（已知豁免）
7. **超大文件 write 工具会失败**：单次 write 输入有大小限制（~5KB），写大文件时分片 + 字节级拼接（参考 specs/plans 当时的处理方式）

## 七、子智能体驱动开发的工作流（推荐继续沿用）

### 流程模板

每个任务（或合并的任务组）按以下顺序：

```
1. 实现者子智能体 (general agent)
   - 输入：完整任务文本 + 必要上下文 + 当前仓库状态 + 提问机会
   - 输出：DONE/DONE_WITH_CONCERNS/BLOCKED/NEEDS_CONTEXT + commit SHA
   - 严格 TDD：红 -> 绿 -> commit

2. 规格审查者子智能体 (general agent)
   - 输入：任务规格 + 实现者声明 + 真实文件路径
   - 任务：独立读真实代码，逐项比对规格（不信报告）
   - 输出：符合规格 或 发现问题（带 file:line）

3. 代码质量审查者子智能体 (general agent)
   - 仅在规格审查通过后进入
   - 输入：BASE_SHA、HEAD_SHA、文件清单 + 已知非阻断瑕疵
   - 任务：整洁/可维护/Go惯例/测试质量四维度
   - 输出：优点 + 问题（CRITICAL/IMPORTANT/MINOR）+ PASS/NEEDS_FIXES/FAIL

4. 修复 IMPORTANT/CRITICAL 问题（控制者直接 Edit 或再分派实现者）

5. 更新 todo + 进入下一任务
```

### 任务粒度建议

- **机械性任务（如 M1-7 Action 类型）：** 控制者直接执行，跳过子智能体
- **小任务相邻可合并：** M1-3+M1-4 已验证可行；M1-5+M1-6、M2-1+M2-2 推荐合并
- **核心任务必须独立：** M1-9 Diff（规格标"核心核心"）、M2-5 executor、M3-6 apply 各自独立分派
- **测试类任务（M4 集成测试）：** 需本机有 svn 二进制；可批量但易超时

### 上下文管理

- 实现者子智能体不要让它读规格/计划文件，**控制者直接粘贴任务文本**
- 审查者子智能体允许读真实代码，因为这是审查的本质
- 每完成 2-3 个任务，主动评估上下文占用，必要时切换会话
- 单任务平均消耗 ~10% 上下文，控制者应在 ~70% 时启动新会话交接
